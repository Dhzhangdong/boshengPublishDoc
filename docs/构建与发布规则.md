# 产品文档构建与发布规则

## 技术分享文章

直接扫描 `技术分享/*.md`，不设置产品级目录，不要求文件名前有序号。README 和子目录中的 Markdown 不作为文章。每篇文章必须有且只有一个一级标题，标题用于文章菜单和列表；地址由文件名去掉 `.md` 后生成，例如 `/articles/context-protocol-lessons.html`。改标题不改变地址，修改文件名会改变地址。`index.md` 和 `_print.md` 为保留文件名。

`/articles/` 与 `/articles/index.html` 显示文章列表；文章及左侧菜单按文件 Git 最后提交时间从新到旧排列，时间相同时按文件名排序。本地尚未提交的文章排在末尾，显示“尚未提交”；正式构建拒绝未提交文章。正文中的实验日期不参与排序。正文、HTML 元数据、sitemap 和 PDF 同样使用文件 Git 历史。

`articles.json` 单独配置名称、发布主体、公开 HTTPS origin 和 `/articles/` 路径，目前沿用 AI接待员域名。产物为 `dist/articles/`，包含列表、独立文章、sitemap 和 `pdfs/<文件名>.pdf`，不生成产品式整本手册。文章使用完整静态正文、Article 结构化数据和独立 canonical；列表使用 CollectionPage 与按实际顺序排列的 ItemList。PDF 的章节、附件超链接指向公开地址。

仅复制文章明确引用的本地图片及 JSON、PDF、TXT、CSV 附件。附件应为技术分享目录内的实际文件；缺失附件导致构建失败。未引用的 QA 轨迹、原始 Markdown、脚本和仓库文件不发布。文章相对 Markdown 链接转换为 HTML，跨产品链接使用该产品的公开地址。

仓库会镜像到公开 GitHub，因此原始请求、消息历史、工具轨迹和推理快照不得提交，即使它们未被构建脚本复制。`技术分享/qa/` 仅保留经过审阅的 `report.json`、`experiment-plan.json` 和 `cold-request-hashes.json`；公开报告移除内部应用、账户、运行标识以及对原始记录文件的引用，并说明公开材料的范围。实验计划中的合成测试题与请求内容哈希可以保留。

完整 `npm run build` 同时生成产品与文章。`npm run build:articles` 只更新文章，清理旧文章输出并保留已有产品页面及 manifest；此命令不验证未登记的其他产品目录，也不要求无关产品源稿已提交。用 `npm run verify:articles` 单独验证文章。增量构建适合本地编辑，CD 始终使用完整严格构建与验证。预览入口为 `/articles/`，也可用 `npm run preview -- articles` 打开专门预览。

## 内容与产品目录

唯一维护源为 `产品手册/<产品目录>/`。每个产品在 `products.json` 登记稳定标识、目录、名称、公开 HTTPS 来源、`/doc/` 前缀和发布主体；菜单从目录直接包含的编号 Markdown 自动生成，不手工维护。

`01 产品介绍.md`、`01-产品介绍.md`、`01_产品介绍.md` 均有效。数字前缀按整数排序，显示名称去掉序号及分隔符；地址按序号生成，例如 `01.html`、`02.html`、`10.html`。修改名称不改变地址，修改序号会改变地址，已有公开章节应保持序号稳定。同产品重复序号（含 1 与 01）构建失败。每章必须有且只有一个一级标题。无序号 README 不进入章节菜单，源文档的 README 链接转换为对应说明入口。

产品手册仅扫描产品目录直接包含的章节；图片可以位于其子目录。新增含编号章节的产品目录必须补充产品公开地址配置。技术分享使用独立的文章列表，不纳入产品说明菜单。

## 默认页面与资源

`/doc/`、`/doc/index.html` 返回序号最小章节的完整内容并选中菜单；该章节主要地址为 `/doc/01.html`（以实际序号为准），首页 canonical 指向主要地址。暂不生成 home 或无扩展名别名。不存在的章节返回 HTTP 404。

章节、图片、CSS、逐章 PDF 和整本 PDF 都经公开 `/doc/` 路径访问。Markdown 相对章节链接转换为对应 HTML；跨产品章节链接指向该产品配置的公开地址。资源须在产品目录内，不发布原始 Markdown、服务端脚本或仓库文件。HTML 禁用源 Markdown 内的原始 HTML 执行。

## Git 更新时间

每章按 `git log --follow --format=%cI -- <文件>` 的最近提交生成“文档最后提交”，保留提交时区的 ISO 时间，界面显示北京时间。不是构建时间，也不是文件系统 mtime。重命名跟随文件历史。HTML 的 time、TechArticle dateModified、sitemap lastmod 及该章 PDF 使用同一个提交时间。整本 PDF 封面使用所有章节提交时间中的最近值，每章仍标自己的时间。

本地未提交修改显示明确提示；新文件没有历史时显示“尚未提交”，不编造更新时间。CD 用完整历史（fetch-depth: 0），拒绝浅克隆及未提交文档。源内容提交后再触发生产构建。图片的独立修改不冒充 Markdown 的提交时间。

## HTML 与 PDF

HTML 为静态完整正文，左侧真实链接菜单、右侧正文；禁用 JavaScript 仍可阅读及跳转。移动端菜单使用原生可折叠控件。输出独立标题、描述、唯一 H1、canonical、Open Graph、TechArticle、产品官网入口及 sitemap；JSON-LD 与可见文字和更新时间一致。源稿可以使用编号标题、表格、步骤、FAQ 和截图说明。

每章生成 `pdfs/<序号>.pdf`，另生成 `pdfs/manual.pdf`。PDF 使用同一 Markdown，包含中文字体、原图、目录、章节时间和页码；整本内部章节链接跳到相应章节，单章中指向其他章节的链接使用公开 HTML 地址。PDF 无外部资源请求，缺失图片使构建失败。PDF 为下载版，以 X-Robots-Tag: noindex 将 HTML 作为主要搜索入口。

PDF 使用目录与书签导航，不重复打印源稿的“说明书目录 · 上一章 · 下一章”纯导航段落；正文中的普通链接仍保留。

发布前检查自动链接验证和 PDF 渲染，尤其是长表格、中文、截图及分页。索引和 AI 引用不保证；提供准确、可抓取的官方内容是基础。

## 本地命令

需要 Node.js 22+、Git。首次安装后安装 Chromium：

```powershell
npm ci
npm run browser:install
npm test
npm run build
npm run verify
npm run preview
```

预览地址 `http://127.0.0.1:18120/doc/`，可以用 `npm run preview -- ai-reception` 指定产品。只生成 HTML 使用 `npm run build:html`；该模式不提供 PDF，不能执行完整 verify 或部署。`DOC_BROWSER_EXECUTABLE` 可显式指定已有兼容 Chromium 的路径，正常环境默认使用 Playwright 安装的版本。

输出为 `dist/products/<产品标识>/`，生成物不提交。`dist/manifest.json` 记录源文件及实际 Git 时间，便于核对。

## Gitea CD

仅 `.gitea/workflows/cd.yml`：main 推送自动构建发布，亦支持手动触发；GitHub 不配置 Actions。CD 在 Docker 构建中执行测试、严格 Git 时间校验、HTML/PDF 构建、链接和输出验证，然后推送 SHA 标记的镜像，部署到现有服务器。发布脚本有独立锁、健康与页面/PDF检查、失败恢复旧版本。

配置和服务器要求见 [CD 部署说明](../deploy/test/README.md)。代码或文档的本地改动不会自行上传、触发远程 CD 或更改现有产品代理。
